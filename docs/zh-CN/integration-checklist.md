状态：2026-11-16。当前所有开发成果位于 Draft PR 链，未合并 `main`；以下检查不等同于真实数据库和身份提供方的生产验收。

## 分支与集成顺序

- `main` 为基线；本轮检查前的头分支 `feat/invitation-rate-limits` 比 `main` **领先 22 个提交、落后 0 个提交**。本检查改动自身作为第 23 个提交置于其后。
- 检查时有 22 个开放 Draft PR（#1–#22）；当前集成验证 PR #23 继续堆叠在 #22 之上。它们按顺序依赖：#1 以 `main` 为目标，#2 以 #1 的分支为目标，依次类推。
- **请勿逆序合并**或把当前每个 PR 直接改为指向 `main`；在同一个链中这样做容易把前序改动重复呈现。
- 首选方案是从 #1 开始，逐个完成评审与 CI 验证，然后按照顺序合并。每次合并后检查后继 PR 的 base、diff 和检查状态；若 GitHub 未自动调整，需重新确认目标分支或重建相关 PR。合并属于有外部影响的操作，必须由维护者明确授权。
- 在实际集成前应确认每个 PR 的文件变更、迁移顺序和审查状态；不要仅依据最新头分支的本地测试得出所有历史 PR 都有独立可合并性的结论。

## 本地可重复检查（不访问真实数据库）

在仓库根目录执行：

```bash
corepack pnpm install --frozen-lockfile
corepack pnpm typecheck
corepack pnpm db:migrations:check
corepack pnpm test
```

`pnpm test` 先构建整个 workspace 再运行测试，避免干净检出时缺少被测试依赖包的 `dist` 而报错；构建失败也会导致测试命令失败。迁移检查只校验 Drizzle 迁移文件的一致性，不会连接或修改 MySQL。

## 实际 MySQL 8.0 联调（待用户授权）

1. 确认用户已有 Docker MySQL 8.0 的容器状态、端口映射以及 ForgeKit 独立数据库和最小权限账号。**不要要求用户贴出密码。**
2. 用未提交的本地环境变量配置 `DATABASE_URL`。先执行 `corepack pnpm --filter @forgekit/db db:check`，该检查只 Ping 数据库。
3. 备份目标数据库，核对 `0000`–`0007` 迁移及 Drizzle 迁移日志，确认没有未受管的表、重复数据或生产数据冲突；得到明确授权后才执行迁移。
4. 验证 `/api/v1/ready`、项目创建/列表/详情/成员查询、资产计划、重复项目名称冲突以及数据库断连的错误反馈。
5. 使用真实 OIDC 测试两个不同账号：Owner 管理成员、Viewer 无法越权；邀请创建、领取、撤销、并发兑换和 429 限流边界。
6. 特别对 MySQL 并发事务、隔离级别、时区和时间精度进行验证；并在使用网关时验证真实来源 IP 的限制与日志脱敏。
