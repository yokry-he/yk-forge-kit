# 构建失败诊断（B26）

当构建状态为 `failed` 或 `timed_out` 时，构建详情页的原始日志上方显示「失败诊断」卡片。成功、排队、运行中或已取消的构建不显示。卡片包含诊断标题、失败原因（1–2 句）与 2–4 条修复步骤；点击「查看相关日志行」可以直接跳转到日志中对应的位置。诊断结果是系统根据退出码、错误码和日志关键字自动判断出来的，仅供参考，请以完整日志为准。日志摘录复用构建日志脱敏工具，在截断前替换已知环境变量敏感值、凭据与令牌。请勿在源码或日志中主动输出凭据；未被工具识别的任意敏感文本无法保证自动识别。

## 诊断类别一览

| 分类 ID | 中文标题 | 常见日志特征 | 典型原因 |
| --- | --- | --- | --- |
| `dependency_registry_network` | 依赖源网络异常 | 拉取依赖超时、连接被拒绝、DNS 解析失败 | 构建环境访问依赖源不稳定或被阻断 |
| `dependency_lockfile_mismatch` | 锁文件与配置不一致 | 提示 lockfile 与 package.json 不符 | 修改了依赖声明但没有同步锁文件 |
| `dependency_missing_package` | 依赖包或版本不存在 | 找不到某个包或某个版本 | 包名写错、包版本错误、私有包访问权限不足 |
| `install_network_disabled` | 安装阶段禁止联网 | 安装步骤被阻止联网 | 平台默认关闭安装联网，未由管理员开启 |
| `compile_error` | 代码编译错误 | 语法错误、类型错误、模块解析失败 | 源码或类型定义有问题 |
| `out_of_memory` | 可能内存不足 | 进程被终止、内存溢出提示 | 依赖体积大或构建并发过高 |
| `timeout` | 构建超时 | 超过最长构建时间被中断 | 安装或构建耗时超出上限 |
| `runner_unavailable` | 构建环境不可用 | 无法连接执行环境、worker 离线 | Docker、镜像或任务执行进程异常 |
| `artifact_missing` | 构建产物缺失 | 构建成功但未找到输出文件 | 输出目录配置与实际产物不一致 |
| `unknown` | 暂未识别失败原因 | 未匹配到已知特征 | 其他原因，需要人工查看日志 |

## dependency_registry_network（依赖源网络异常）

构建过程中需要从依赖源下载包，但网络连接不稳定或被阻断，导致下载失败。

1. 稍等几分钟后重新触发构建，排除临时的网络波动。
2. 确认项目使用的依赖源地址填写正确，没有指向不可用的地址。
3. 如果依赖源需要代理才能访问，请联系管理员确认构建环境的网络配置。
4. 请管理员确认所用依赖源当前可以正常访问。

## dependency_lockfile_mismatch（锁文件与配置不一致）

依赖声明文件被改动后，锁文件没有同步更新，安装时校验不通过。

1. 使用与构建环境一致的包管理器更新依赖与锁文件，并将两者一起保存在构建使用的源码中。
2. 检查是否有人手工修改过锁文件，如有请恢复为自动生成的内容。
3. 确认本地与平台的 Node、pnpm 版本一致，避免生成格式不同的锁文件。
4. 确认修复进入本次构建使用的源码后，重新触发构建。

## dependency_missing_package（依赖包或版本不存在）

构建时找不到某个依赖包或指定版本，安装步骤直接失败。

1. 检查日志中提示的包名是否拼写正确，以及它是否已写入依赖声明。
2. 确认该包和对应版本在依赖源中存在。
3. 如果是私有包，请确认依赖源已配置访问凭据，并且当前账号有权限。
4. 修正后重新触发构建。

## install_network_disabled（安装阶段禁止联网）

安装阶段失败、容器的安装网络策略为 `none`，且日志或错误码包含 DNS、连接、依赖源拉取或 Corepack 下载失败等网络证据时，平台显示此提示。Node 版本不兼容不会仅因禁网策略归入此类；prepare 钩子中的类型或编译错误归为 `compile_error`，其他未匹配故障归为 `unknown`。`FORGEKIT_BUILD_INSTALL_NETWORK` 默认为 `none`；管理员可以评估设为 `outbound`，或使用 `registry` 受控代理策略。`registry` 还要求配置 `FORGEKIT_BUILD_REGISTRY_NETWORK` 与 `FORGEKIT_BUILD_REGISTRY_PROXY`，具体约束见 [Docker Runner](./docker-build-runner.md)。源码编译阶段始终断网。

1. 联系管理员检查 `FORGEKIT_BUILD_INSTALL_NETWORK` 的实际取值与网络策略。
2. 由管理员按需评估 `outbound` 或 `registry` 策略，并确认配置对当前 Worker 生效。
3. 配置生效后重新触发构建。
4. 如果出于安全考虑不能开启联网，请与管理员一起评估依赖的获取方式。

## compile_error（代码编译错误）

代码本身存在语法、类型或模块引用问题，构建过程在编译阶段中断。

1. 在日志中找到第一条报错，记下它指出的文件和行号。
2. 在本地复现并修复该问题，确认本地构建可以通过。
3. 检查是否缺少类型声明或依赖版本不匹配。
4. 提交修复后重新触发构建。

## out_of_memory（可能内存不足）

日志明确提示内存耗尽，或退出码为 137 时显示此提示。137 代表强制终止，也可能由超时或其他原因造成，需要管理员结合容器记录核实；已知超时信号优先归为 `timeout`。

1. 检查是否引入了体积很大的依赖，或构建过程占用了过多内存。
2. 适当降低构建并发，减少同时进行的任务数量。
3. 联系管理员评估 `FORGEKIT_BUILD_MEMORY_MB` 内存上限和系统终止记录。
4. 再次触发构建，观察是否仍出现内存不足。

## timeout（构建超时）

安装或构建耗时超过了允许的最长时间，任务被中断。

1. 查看日志最后停在哪一步，判断是哪一步耗时过长。
2. 检查依赖安装是否反复重试，或构建过程存在卡住的任务。
3. 联系管理员评估 `BUILD_TIMEOUT_MS` 是否满足项目需要。
4. 精简依赖与构建内容后重新触发构建。

## runner_unavailable（构建环境不可用）

平台无法连接到实际执行构建的环境，任务没有真正开始或中途丢失。

1. 请管理员检查 Docker 守护进程是否在正常运行。
2. 请管理员检查 Worker 和队列，以及 `FORGEKIT_BUILD_IMAGE` 对应镜像是否已在主机准备好；Runner 使用 `--pull=never`，不会自动拉取镜像。
3. 如果刚刚重启过环境，等待其恢复后再试。
4. 重新触发构建，确认问题是否仍然存在。

## artifact_missing（构建产物缺失）

构建流程结束，但平台在预期位置没有找到输出目录或入口文件，或产物存储目录不可用。

1. 检查模板中构建输出目录的配置（如 `dist`）是否与实际生成的目录一致。
2. 确认构建命令确实产出了文件，而不是只做了检查或跳过。
3. 检查输出路径的大小写和嵌套层级；请管理员核对 `FORGEKIT_ARTIFACT_DIR` 目录及写入权限。
4. 修正配置后重新触发构建。

## unknown（暂未识别失败原因）

当前失败原因没有匹配到已知类别，需要人工查看完整日志。

1. 点击「查看完整日志」，找到最早出现的实际报错。
2. 记录报错内容、构建时间和构建 ID。
3. 将构建编号、时间与已脱敏报错反馈给管理员或平台维护者，勿发送密钥。
4. 如条件允许，在本地按相同步骤复现问题，便于进一步定位。

## 日志定位与历史记录

「查看相关日志行」使用数据库日志块的 `seq` 定位并高亮，关闭自动滚动，并将键盘焦点移到日志区域。一个日志块可能包含多行，因此高亮可能覆盖整块。若日志尚在加载，会在对应块到达后定位；超出日志视图最近 5000 块 / 2 MiB 保留范围时，页面提示结合上方摘录排查。

没有匹配日志（例如 Docker 尚未启动就失败）时，显示「查看完整日志」。旧失败构建的 `diagnosis` 为 `null`，不补算历史日志，显示「暂未识别失败原因」和通用步骤。迁移不改变原有构建状态与日志。

当前构建来源仍受模板来源能力限制，不能把本地 Git 提交等同于平台已经读取该提交。请核对详情中的来源引用；来源边界见 [构建控制台](./build-console.md)。

## 给管理员 / 开发者

诊断分类规则在代码中维护，根据退出码、错误码和日志关键字进行匹配。新增或调整类别时，请同步更新本文档的类别表格与对应小节，并在单元测试中补充该类别的样例日志，确保规则与文档保持一致。


### 实现与 API

- 纯分类器及 schema 位于 `packages/contracts/src/build-diagnosis.ts`；脱敏函数位于同包的 `build-log-redaction.ts`，Worker 原入口继续导出相同函数。没有外部 AI 调用或新增依赖。
- Worker 根据退出码、固定错误码、安装/编译阶段及网络策略分类；仅允许列出的内部异常码参与诊断，不保存任意异常文本。优先使用明确超时、OOM、Runner 和产物信号，其次按固定顺序匹配锁文件、包缺失、禁网、依赖源网络及编译错误。网络类日志只在非编译阶段作为安装故障处理。规则是启发式判断，可能误判。
- 日志在持久化时脱敏；诊断再次对完整日志块脱敏后才截断。Worker 仅保留最近 5000 块 / 2 MiB 作为本次诊断输入。每条诊断至多关联 3 个日志块，摘录至多 3 行，每行至多 240 个 UTF-16 代码单元，按 Unicode 码点边界截断，并将输入中的孤立代理项替换为 `U+FFFD`，避免生成 MySQL JSON 无法接受的文本。
- 终态写入若携带诊断失败，Worker 会保留原状态、退出码、错误消息及其他字段，重试一次不含诊断的写入；状态转换守卫仍生效，取消等已完成终态不会被覆盖。
- `builds.diagnosis` 为可空 JSON，内容为 `{ category, matchedLogSeqs, excerpt }`。迁移为 `packages/db/drizzle/0019_b26_build_failure_diagnosis.sql`，必须先应用迁移再部署应用。
- 现有 `GET /api/v1/projects/:projectId/builds/:buildId` 在 Build 对象中返回 `diagnosis`；列表和日志流的 Build 状态对象也使用相同契约。继续检查 `build:read` 项目权限与构建归属；没有新增匿名读取入口。
- 本功能沿用 ADR-0008/0010 的依赖与授权边界，不引入新技术路线。回退应用可保留可空字段，无须删除构建或日志；不要对生产数据直接执行逆向删列。

### 验证与翻译状态

分类样例、脱敏边界、Worker 写入、API 权限/读取与控制台交互有自动化测试；数据库仓库的 MySQL 测试覆盖 JSON 往返。真实 Docker、MySQL 与浏览器主题/布局验收需在相应环境单独执行，不能从单元测试推断已验证。
