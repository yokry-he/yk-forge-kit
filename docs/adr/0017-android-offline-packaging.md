# ADR-0017: Android packaging on customer infrastructure

- Status: Accepted for B18 implementation; real SDK/device acceptance pending
- Date: 2026-11-22

## Decision and feasibility

B18 adds an independent `android` BullMQ job, not a static deployment or a WeChat upload. The worker renders the registered **uniapp template** using a persisted project slug/features snapshot, injects public AppID/version metadata, installs npm dependencies with B09's existing policy, then runs `build:app` inside a separate offline container. The source boundary remains B09's template reconstruction: no local checkout, Git snapshot upload, arbitrary Gradle project, UTS or native plugin integration is implied. B14 environment variables are deliberately not forwarded: signing must never become a frontend variable. Resource compilation is production compilation for both debug/release; native debuggability and certificate distinguish the two.

The official [uni CLI documentation](https://uniapp.dcloud.net.cn/worktile/CLI.html) supports Vue 3 `uni build -p app` to produce offline App resources; it does not produce an APK. The [official offline SDK](https://nativesupport.dcloud.net.cn/AppDocs/) and [Android integration guide](https://nativesupport.dcloud.net.cn/AppDocs/usesdk/android) provide the runtime, native shell, assets/data and AppKey configuration. B18 uses these resources with a trusted, repository-owned Gradle shell, then signs in another container. We do **not** substitute an H5 WebView wrapper for uni-app App runtime.

No DCloud cloud packaging call, account login or HBuilderX installation occurs in a job. HBuilderX CLI depends on its host installation and cloud packaging is a vendor service, so neither fits a Linux isolated self-hosted runner as well. Community packagers often automate the same proprietary runtime and add another dependency/license boundary; none is introduced. The official runtime is **not an open source replacement for DCloud**: the operator must obtain a licensed matching SDK and register AppID/AppKey and package/certificate fingerprints. Image creation needs internet access for Android/Gradle/Maven downloads; npm installation needs a permitted registry or a prepared cache. Runtime native build/signing is offline. App behavior may still require internet, and offline packaging does not remove vendor runtime requirements.

## Toolchain and delivery

`infra/android/Dockerfile` pins Temurin JDK `17.0.17_10` (Jammy), Android command-line tools archive `13114758` (19.0), platform `android-36`, build tools `36.0.0`, Gradle `8.14.3`, AGP `8.12.0`. This follows the DCloud guide's post-4.81 API 36 / 16 KiB toolchain requirements; AGP 8.12 [supports JDK 17/API 36](https://developer.android.com/build/releases/agp-8-12-0-release-notes). The compiler stays B16's `3.0.0-5030420261029002` ([official published compiler metadata](https://registry.npmjs.org/@dcloudio/vite-plugin-uni/3.0.0-5030420261029002) reports compilerVersion 5.34); the private normalized runtime archive is explicitly `dcloud-5.34.tar`, with `VERSION=5.34`. Operators must check the vendor release notes for exact compiler/runtime compatibility; the label alone cannot prove matching binaries. Native integration is a candidate pending a real licensed SDK build and device test, not a claim that a vendor archive was downloaded or certified here.

Command-line-tools, Gradle and the private SDK archive require operator-verified SHA-256 build arguments. The image build compiles both APK and AAB, then repeats both with `--offline` before acceptance; missing SDK libraries or Maven cache fail image creation. Only required Android packages are installed (no emulator/NDK). No Maven/SDK installation occurs in jobs, and `android.builder.sdkDownload=false` is set. The trusted shell fixes Maven coordinates; changes to SDK/modules require reviewing and rebuilding the image. The default dependencies follow the vendor guide rather than an unverified community wrapper. Google Play prohibits the vendor install-apk module; operators must omit that optional AAR for Play distributions and validate the intended store requirements. Basic template packaging does not imply payment/push/map/privacy compliance.

The npm image is separate and operator-provisioned with Node 22 and Corepack/pnpm 10.18.3 (example `node:22.21.1-bookworm`). Existing B09 environment selects it; production must pin both images by digest and scan/rebuild them, including JDK security updates. The native image never inherits the Node build image, so it does not ship npm/project dependencies. SDK/AAR files are intentionally absent from Git and CI; `infra/android/vendor/` is ignored. SDK redistribution, Android license acceptance and private image storage belong to the operator. JDK is GPLv2 with Classpath Exception, Gradle/AGP primarily Apache-2.0, Android SDK and DCloud runtime have separate vendor terms. No npm dependency or lockfile change is required. Python 3 standard library is the trusted native/sign adapter; replacement is confined to the worker runner/image.

## Secrets and isolation

`android_configs.settings` stores public package/AppID/AppKey/version fields. AppKey is embedded in AndroidManifest.xml and readable by project members; it must not be treated as a signing credential. Keystore (max 64 KiB, Base64 transport), alias and both passwords form one AES-256-GCM authenticated envelope using B14's `FORGEKIT_DEPLOY_ENCRYPTION_KEY`, fresh IV and `b18:<project UUID>` AAD. Only metadata and `hasSigning` are readable; no signing read/decrypt API, ciphertext response or request-body audit. Errors use fixed Chinese text, never raw Zod/SQL/crypto/tool error messages. Base64/body/password limits keep requests under the existing 100 KiB JSON parser budget. Actual keystore/password/certificate compatibility is verified by the isolated signing tools, not by invoking Java on the API host. Invalid material can be saved but fails packaging without revealing diagnostics.

Config writes/deletes and triggers serialize on the project lock (`READ COMMITTED`), and are rejected while a job is queued/running. Changing package name without a replacement clears signing. Jobs snapshot public settings/source metadata, never credentials; the worker validates current release config before decrypting. Debug never decrypts release signing. The image generates a development JKS **once per image**; its fingerprint is exported as `/opt/android/debug-certificate.txt` for AppKey registration. Rebuilding the image changes that certificate unless the same built image is retained; debug is not a production identity. Per-job random debug keys were rejected because AppKey registration binds certificate fingerprints. Store users must maintain their own release key and backups. AAB uses JAR signing; APK uses zipalign (16 KiB), apksigner, verification and aapt package/version validation.

Compile/install/native containers receive no signing values. After compiled output passes ArtifactStore path/link/count/size checks and AppID validation, the native container reads only the resource snapshot, not node_modules or source build configuration. Gradle shell/cache come only from the trusted image; no caller-supplied executable Gradle is loaded. The native container outputs only a fixed unsigned archive. The **sign container** mounts only that output and public job metadata. Credentials enter via stdin (no secret argv/env/bind mount). The trusted Python entry drains the pipe, writes 0600 key/password files only into `/tmp` tmpfs, invokes fixed signing tools, suppresses all signer diagnostics, and removes temporary key/password files in finally. No keystore/password is copied into source, resource assets, source maps, Gradle files, layers, host workspaces or published artifacts. Passwords use tools' `file:` password options, not literal command arguments. Neither the native nor signing container executes project scripts. Signing tools necessarily parse the unsigned archive; their security still matters.

All phases reuse B09 Docker CLI cleanup: non-root worker UID/GID, read-only root, dropped capabilities, no privilege escalation, default seccomp, no Docker socket/host mounts, `--pull=never`, log-driver none, unique names. Native/sign use network none, 2 CPU, 4 GiB RAM with equal memory-swap, 256 PIDs, no core dumps, bounded file descriptors and 2 GiB /tmp tmpfs. Npm install uses B09 none/registry/explicit-test-outbound policy; compile always has no network. Set a dedicated execution host and disk quota; a proxy variable alone is not egress enforcement. Native caches/workspaces are per job, never shared writable across tenants.

Each phase has a 600-second in-container deadline; the processor aborts after 30 minutes. Cancellation remains running until runner cleanup completes, and the worker observes the request every second; a concurrent success CAS cannot override a committed cancel request. Abort/shutdown await runner cleanup. Confirmed container removal precedes host traversal/publication; uncertain removal preserves the private workspace and fails the task. SIGKILL/daemon outage can still leave containers; operator recovery must confirm their deletion before removing directories. Docker shares the kernel and privileged operators can access process memory/tmpfs. JS strings cannot be reliably erased; decrypted Buffers are wiped. B14 redaction cannot detect arbitrary encoded leaks, so separation of signing from project code is the primary defense.

## Persistence, API and console

Incremental migration `0016` adds android_configs/jobs/log_chunks/audit with Drizzle snapshot/journal; no existing build target/row changes. Queue payload is strictly `{ jobId }`, with ID deduplication and B08's 30-second queued reconciliation. Reclaimed running jobs fail instead of executing twice; orphan running jobs are reconciled after 30 minutes plus 60 seconds. Terminal jobs cannot be restarted; retries create a new job. Cancellation audit contains only IDs/action/actor. No exactly-once artifact/SQL commit guarantee: worker loss after publishing but before committing may leave an orphan requiring retention work.

Only existing OIDC project permissions apply: deploy:manage for config, deploy:run for trigger/cancel, deploy:read for history/logs/download; owner/editor mutate, viewer reads, unknown/local fail closed. Identity writes use a distinct android-write quota (60/hour). API trigger requires image configuration; it does not probe remote consumer health. Logs are capped at 1 MiB, line-reassembled and redacted before 16 KiB chunks/persistence. SSE uses B17's independent single-use 60-second hashed tickets, Last-Event-ID/cursor recovery, permission rechecks, high-water terminal draining, backpressure and connection limits. Console uses Element Plus and Chinese copy; logs render as sanitized text.

Only validated signed `app.apk` or `app.aab` is copied into a dedicated ArtifactStore publish directory (max 256 MiB). Metadata includes kind, raw-file SHA-256, size, snapshot package/version and debug/release. This digest is distinct from ArtifactStore's directory-manifest SHA-256. Store keys stay internal. Download requires membership and returns no-store/nosniff attachment; the console verifies the raw SHA-256 before saving. No public preview link or source map/resource download is added.

## Validation, limits and rollback

Default CI uses mocked Docker/queue/native/signing tools, strict contracts, encryption/AAD/tampering, generic errors, HTTP role checks, final SSE logs, processor cancel/shutdown/cleanup, artifact metadata and console interaction/resume tests. Python stdlib tests exercise signer arguments, tmpfs file cleanup, APK/AAB branches and failure redaction without installing Android tooling. MySQL tests are opt-in with the existing integration database. The production image build itself is an opt-in expensive smoke path and must pass online warmup plus offline APK/AAB tasks; CI does not pull an unpublished image or install Android SDK on each PR.

A successful mocked test is **not** a real Gradle, device or app-store acceptance. Before enabling for users, build/scan the licensed image, run debug/release APK/AAB jobs, verify signatures/metadata/checksums and cancellation cleanup, install an APK and exercise all template tabs/data/navigation with the registered AppKey on a real Android device. Check AAB through the chosen store/bundle tooling. No Docker daemon/JDK/private SDK/account/device was available for the implementation environment; those checks are explicitly unverified.

Rollback: disable trigger/config endpoints operationally and unset FORGEKIT_ANDROID_IMAGE after draining/canceling jobs; stop consumers, inspect residual containers, retain migration tables/logs/artifacts and the B14 master key. Revert application code, prefer forward repair; no automatic destructive reverse DDL. Existing H5/WeChat flows remain independent. Public release requires matching English key user guides (Chinese is authoritative now).

Deferred: immutable source/Git ingestion and project lockfiles, native/UTS plugins, custom permissions/icons/modules, automatic artifact/log retention and orphan GC, KMS/rotation, store upload/review, exact binary reproducibility and dependency verification expansion. **iOS packaging is a next step only**, requiring a separate macOS/signing/Apple-account design; no iOS job is delivered by B18.
